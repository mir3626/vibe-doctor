# v1.14.0 - Deterministic Goal Ownership and Safe Pro Operator Close

Date: 2026-08-31

This release closes two lifecycle ambiguity gaps that could redirect otherwise
valid work: a standalone goal iteration could inherit an unrelated ambient Pro
pointer, and a bare Pro invocation could select or scaffold a mistaken flow
before the user had identified the intended target. The same release adds a
durable, user-authorized terminal for flows that cannot safely continue through
the normal approval/close protocol.

## Durable goal-iteration ownership

- Active iteration history now carries an optional strict `executionBinding`.
  `standalone-goal-iterate` requires `proFlowPath: null`; `pro-roundtrip`
  requires one exact flow path.
- A valid standalone binding ignores but never mutates unrelated ambient Pro
  state. An exact Pro binding still requires the matching active flow and
  cumulative checkpoint at the current HEAD.
- Legacy iteration records without the new field keep the pre-release ambient
  Pro gate. Missing or ambiguous ownership therefore remains fail-closed.
- Historical Sprint replay cannot attach an old completion to a newer current
  iteration or bypass a same-named active legacy Pro flow.
- Goal planning, iteration phases, Planner guidance, report routing, completion
  runtime, schemas, and sync-owned workflow documentation share the same rule.

## Bare Pro invocation is inspection-only

- Bare `$vibe-pro-go` and `npm run vibe:pro-go` read only the current checkout
  identity, local `ACTIVE.json`, and local auto-publish configuration. The JSON
  result explicitly reports `scope: local-pointer` and
  `scaffoldingCreated: false`.
- Bare execution never fetches `vibe-pro-bridge`, selects a remote flow, syncs,
  bootstraps, starts, or creates packet/worktree scaffolding.
- Resume is explicit through `go <exact-flow>` or a qualified `--date` /
  `--slug` selector. Unqualified `go` may use only a valid checkout-owned local
  active pointer.
- Default-flow consumers use the active local pointer rather than a
  lexicographic latest-flow fallback.

## Deterministic operator force-close

Use a dry-run first:

```bash
npm run vibe:pro-go -- force-close <flow> --reason "<one-line reason>"
```

Publish only after fresh approval for the exact flow and identical reason:

```bash
npm run vibe:pro-go -- force-close <flow> --reason "<same reason>" --publish --user-approved
```

- `proGoAutoPublish` never satisfies the approval requirement.
- Publication adds only `<flow>/OPERATOR-CLOSE.json` in an isolated append-only
  commit. The strict record binds the flow path, repository, code branch, base
  SHA, current code HEAD, and source bridge SHA.
- Loader integrity checks require exactly one close-path commit, a single-file
  addition, the source bridge commit as sole parent, and byte-identical
  `FLOW.json` between source and terminal commits. A deleted, rewritten, or
  transplanted close record fails closed.
- Repeating the exact reason is idempotent and can reconcile the matching local
  pointer. A different reason is rejected as an immutable-record conflict.
- A valid record reports terminal `force-closed`, never approved/completed.
  Exact and qualified resume selectors reject it, and one force-closed member
  prevents a coordinated normal close for the entire set.
- The root Web entry runbook checks this operator terminal before the pinned
  protocol and event chain. Poisoned and superseded-generation flows can
  therefore stop safely without rewriting their historical protocol namespace.

## Downstream upgrade

No migration is required. The iteration binding is additive and legacy-safe;
the operator-close schema is generated under `.vibe/harness/schemas/**`, which
is already harness-owned by the sync manifest. After syncing v1.14.0,
downstreams receive the CLI/runtime, shared Claude skill, thin Codex wrapper,
root Web runbook, schema, and regression coverage as one boundary.
