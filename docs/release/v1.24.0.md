# v1.24.0 - The Charter Says Which Rules Apply, and Evidence Must Show What the User Will See

Date: 2026-11-20

## Why

The owner asked a downstream session what the harness had cost it and what it had not caught
(sprite-generator, Claude Fable 5.2 on the Astra profile, 2026-11-18 to 11-20), then asked for the
answer to be applied with quality first. The basis is that one session's report from use. It is not a
paired run with and without the harness, and nothing here measures the quality of what a session
produces.

- `CLAUDE.md` loaded 23.3 KB into every session and again after every context compaction. Under the
  Astra profile the project's own rules were two paragraphs of it, about 1 KB, and the last block of
  the file. Most of the rest described legacy procedure the profile turns off, with legacy imperatives
  ("Orchestrator는 소스코드를 직접 Edit/Write하지 않는다") a few lines from the Astra exception.
- Two defects in a visual deliverable passed every check and the session's own review, and the user
  found both. The session had captures. They could not show the defects: a composite hid a hole in the
  body layer, and front views hid diagonals that looked flat. The rules asked for an evidence item, not
  for what it has to show.
- Every report on a product-code change carried the §14 wiring table with fourteen `n/a` rows.
- The project came from the template, so it had no `sync-hashes.json`. Its first sync (1.22.0 to
  1.23.3) reported 21 conflicts "without sync history". 20 of those files were byte-identical to
  v1.22.0, which the session established by cloning that tag by hand.

## What changed

- `CLAUDE.md` is laid out by what applies, 23.3 KB to 8.9 KB:
  1. which profile follows what (Astra: the project rules and the rules for every profile; legacy: the
     whole file, and `docs/context/charter-extensions.md` before the first Sprint and after a
     compaction; unsure: legacy),
  2. the project rules (`PROJECT:custom-rules`),
  3. the rules for every profile: verification before reporting, what counts as evidence, script
     gates, pace, the sub-agent framing, the shard index, the soft freeze,
  4. the Legacy charter, unchanged in content (headings one level down, two pointers renamed, the
     wiring line scoped).
- The former Extensions moved, text unchanged, to `docs/context/charter-extensions.md` (16 KB): role
  constraints, the trigger matrix, the reasoning policy, the script table with the hook rules, provider
  call mechanics, the Sprint flow, the prompt rules, the skill list and the mode-flag convention. The
  duplicate Astra paragraph inside the core framing is gone; the first section says it once.
- New section `HARNESS:evidence`, for every profile: anything people look at, read or use is seen
  before it is reported, in its default view and state, in every variant it ships in, and each
  separable part on its own. When the user finds a defect a review passed, the session records what the
  review did not look at and adds the check or capture that shows it. `astra-rules.md` carries the
  same two points.
- `_common-rules.md` §14: the W1-W14 and D1-D6 table is for harness-file changes. A product-code
  change reports `verified-callers` for each new file and its tests. W1-W3 name the new places.
  `astra-rules.md` asks for the callers of each new file and nothing else from §14.
- `vibe-rule-audit` reads the extensions with the charter (`--extensions`, on by default unless
  `--claude-md` names a file) and prints which file a rule is in. `vibe-context-audit` scans the new
  shard. The Claude init prompt names the first section as well as the charter block.
- `vibe:sync`: a harness file without a recorded hash that is identical to the installed version's
  copy is replaced (`local copy matches the installed version`). The installed version is the checkout
  the first sync already clones for hybrid files. A file that differs from it, or that the installed
  version never had, is still a conflict.
- Three rows in `harness-gaps.md`. Two are `partial` with `script-gate: pending`: nothing checks that
  a legacy session reads the extensions, and the evidence rule is documentation.

## Downstream impact

- Sync rewrites `CLAUDE.md` to the new layout. `PROJECT:custom-rules` and `SPRINT_ROLES` keep their
  local text and move with the layout, so project rules become the second section. A harness section a
  project edited is reported as a conflict as before; if the project keeps one that upstream no longer
  ships (`role-constraints`, `trigger-matrix`, `reasoning-policy`), it is appended at the end.
- One new harness file, `docs/context/charter-extensions.md`. A project that had moved the script
  table into a shard of its own keeps that shard.
- A sentence in a project's own rules that points at "the rules above" now sits above them; reword it
  after the sync.
- Legacy-profile sessions keep the charter in every session. The detail they used to receive
  automatically now takes one read, which the first section and the shard index both ask for. Not
  tested: no legacy-profile session has been run on the new layout.
- No migration, schema or protocol change.
