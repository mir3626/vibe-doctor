# v1.22.0 - Sync Keeps Downstream Edits in Harness Sections and Keys

Date: 2026-11-04

## What changed

### Sync no longer drops downstream edits silently (B4)

- Before, `vibe:sync` stopped on a locally changed harness-owned file, but the harness sections of
  `CLAUDE.md`, `AGENTS.md`, `GEMINI.md` (section-merge) and the harness keys of `.claude/settings.json`,
  `package.json`, `.vibe/config.json` (json-deep-merge) simply took upstream. A downstream edit there,
  such as a sharded `CLAUDE.md` or a `PreToolUse` hook, vanished without a conflict, and accepting a
  conflict replaced the whole file.
- Sync now records the hash of each harness section and key in `.vibe/sync-hashes.json` (`regions`) and
  compares three versions: what upstream shipped at the last sync, the local text and the new upstream.
  - Only the downstream changed it: the local text stays and the plan says `kept local: …`.
  - Both changed it: a `conflict` row names the sections or keys. Accepting takes upstream there,
    skipping keeps the local text there; either way the file is merged, so project sections and keys
    survive. A skipped section or key is reported again on the next sync.
  - No region history yet (the first sync with this code): sync clones the installed version once as
    the base. If that clone fails, a section or key that differs from upstream is reported as a conflict.
- `--force` takes upstream for every conflict: harness files are replaced, hybrid files take upstream only
  in the conflicting sections or keys. The new `--keep-local` keeps the local side of every conflict and
  applies the rest. Before, a run without a terminal could only use `--force`, so an agent or CI sync had no
  way to keep downstream edits. Gap `gap-sync-silent-hybrid-overwrite` is covered.
- A section is a top-level marker block (`CHARTER`, `EXTENSIONS`, `PROJECT:*` …), the unit the section merge
  has always replaced, so an edit anywhere inside `EXTENSIONS` makes `EXTENSIONS` local.

### Skill and rule fixes from Anthropic's skill-authoring checklist

The chairman of the downstream vibe-office reviewed the harness skills against Anthropic's
"Skill authoring best practices" (2026-11-04). This release applies the documentation findings:

- Contents lists on long reference files: the three `vibe-init` phase shards, both `vibe-pro-go`
  references, `workflow-integrity.md`, `_common-rules.md`, `orchestration.md`, `codex-execution.md` and
  `astra-profile.md`.
- One-level references: `vibe-init` names the test-pattern index, `vibe-iterate` names
  `verification-reuse.md` and `vibe-review` names `harness-gaps.md` directly.
- The `CLAUDE.md` mechanical-overrides sentence no longer says all three rules always apply; under the
  Astra profile only rule 3 (verify before reporting) does, which is what `astra-rules.md` already said.
- `vibe-sprint-mode` asks for a tier once. When a tier is on, or the session log already records the
  choice, it proceeds without asking, and it no longer asks at the end of every Phase whether to turn
  it off. The legacy-only reason for gating `src/**` edits is labelled as such.
- `goal-to-plan`, `write-report`, `vibe-review` and `vibe-sync` descriptions say when to use them;
  `goal-to-plan` says a clear task goes straight to implementation.
- `self-qa` and `vibe-goal-iterate` say what to do when a check fails: fix, rerun the same check, and
  report done only when it passes. `self-qa` runs only the checks a change can affect.
- `vibe-init` gives install commands for its required tools, fixes the version example (v24, matching
  the Node 24 requirement) and drops a stale plugin note.
- The `sprint-planner` comment now says Claude Code uses its `model` when an Agent call passes none;
  `context-curator` and `qa-guardian` lose their persona lines.

## Downstream impact

- Sync updates the harness-owned skills, agents, docs and `.vibe/harness/**`. `CLAUDE.md` takes the
  corrected mechanical-overrides sentence through its harness section.
- The first sync to this version that runs the new sync code compares hybrid files against the installed
  version and may report conflicts for harness sections or keys the project changed on purpose; resolve
  them per file (skip keeps the local text). `npm run vibe:sync` in a downstream still runs that project's
  installed sync code, so the protection starts with the sync after this one unless the new code is run
  directly: `node --import tsx <vibe-doctor checkout>/.vibe/harness/src/commands/sync.ts`.
- `.vibe/sync-hashes.json` gains an optional `regions` map. Older sync code ignores it.
- No migration, schema, protocol or dependency change.
